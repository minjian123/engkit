# 预检耗时治理 · 需求

> 专项域文档：把「预检慢」从体感判断变成可度量、可验收的工程问题

## 1. 域说明 <a id="intro"></a>

**覆盖范围**：engkit 预检引擎（提交环 `.git/hooks/pre-commit` + 推送环 `engkit push`）的**耗时**，不含判据口径变更。

**依据**（实测，2026-11-07 提交环 37 项 / 117.6s）：

| 分段 | 实测 | 占比 |
| --- | --- | --- |
| 前端类型（4 工程 typecheck + desktop build） | 48.8s | 41% |
| 其余步骤启动开销（10+ 检查各起一个解释器） | 约 47s | 40% |
| 定向用例 | 17.9s | 15% |
| 全仓 pyright | 8.2s | 7% |
| 覆盖率采集 | 3.5s | 3% |

推送环约 9 分钟，其中主体是**提交环内容整段重跑**，再叠加全量静态与全部自测。

**目标形态**：同一改动集的第二次预检（推送环）不再重复计算已通过的步骤；护栏检查不再为每条检查付出一次解释器冷启动。

**不做什么**（本域明确排除）：

- 不改覆盖率判定单元（整文件 100% 保持），不建历史缺口基线；
- 不做前端 typecheck 的产物级缓存（`tsc incremental`），二期再议；
- 不允许以「少判」换「少时」——任何跳过都必须满足「同输入且该输入下已通过」。

## 2. 需求 14-1：步骤结果复用 <a id="r14-1"></a>

优先级：1（高）

**背景与动机**：一个任务按纪律最多两次提交（`feat` + `docs`），但推送环会把提交环跑过的步骤整段重跑一遍；同一份代码在两环各自计算一次，被判据判定为「同输入」的部分纯属重复劳动。不做的后果：一个任务的门禁时间由「提交 2 次 + 推送 1 次」线性叠加，实测可到半小时以上。

**内容**（《AI开发规范》§5 补充纪律「慢步骤治理登记在专项待办」）：

1. 步骤通过后按**缓存键**记录结果；缓存键三元组固定为「步骤命令全文 + 工具链版本指纹 + 输入集指纹」，三者缺一不可。
2. **输入集指纹**：步骤在配置里可声明 `inputs`（路径前缀 / glob）；未声明时按命令形态推断——读取全仓的命令退化为整棵树哈希（`git write-tree` 等价物），接收改动清单的命令（`--files-from` / `{files}` 占位）取当次改动文件集的内容哈希。
3. 推断规则**不得出现任何仓名与仓内目录字面**（《工具包开发约定》红线 1）：只能读 `[docs].root` / `[frontend].root` / `[backend].root` 这些既有配置值。
4. 命中条件：键完全相等 **且** 该键下上次结果为通过；命中即跳过该步并打印「复用（上次通过于 …）」与命中的输入集摘要。
5. **失败路径一律真跑**（fail-open 到执行）：缓存缺失、键不相等、文件损坏、读写异常、结构版本不符，全部回退执行并打印回退原因，不得回退成「跳过」。
6. 缓存落 `<仓根>/.cache/preflight/steps.json`（与 `audit.jsonl` 同目录），随 `.cache` 删除即整体失效；另加「命令或工具链版本变更即失效」与 7 天过期两条时效约束。
7. 定向用例段（`scoped_tests`）**本域不参与复用**：其产出是覆盖率采集数据，跳过后 `coverage_report.py` 读到的是旧数据，与「排障只看已采集数据」的口径冲突；该段实测 17.9s，收益不足以承担该风险。

**完成标准**：同一棵树连续两次预检，第二次除「已被判定为输入变化」的步骤外全部命中；改动代码后同一步骤不命中；缓存文件损坏时全部回退真跑且预检结果与无缓存时一致。

**参考文档**：《AI开发规范》§5「单任务交付一条龙」补充纪律、《工具包开发约定》§1 三条红线、《工程化工具包说明》§4.3 预检段

## 3. 需求 14-2：推送环静态范围收窄 <a id="r14-2"></a>

优先级：2（中）

**背景与动机**：推送环的「全量静态」含全仓 `pyright .`。类型检查的成本随被检文件数近似线性增长，而实际受本次改动影响的只有「改动文件 + 反向依赖它们的模块」。不做的后果：推送环为一处局部改动付出整仓类型检查成本。

**内容**：

1. 仅**推送环**的 pyright 步骤支持 `scope = "changed-closure"`；提交环保持全仓 `pyright .`（实测仅 8.2s，收窄的收益不抵漏判风险）。
2. 闭包 = 改动文件 ∪ 反向依赖改动模块的文件（复用 `selection.py` 的模块导入图；反向闭包同样只在该模块实现，遵守「选测推导只有一份实现」）。
3. 退化条件（打印原因，不静默）：改动命中全局输入（后端依赖清单、迁移目录、配置前缀等）、闭包规模超过阈值、改动文件不在任何已登记工程内。
4. 全仓漏判由 CI 的全量静态兜底，本项不改变 CI 判据。

**完成标准**：改动单个叶子模块时推送环 pyright 只检该模块及其反向依赖者；改动基础模块 / 全局配置时退化为全仓并打印退化原因；故意在被检集合外引入类型错误时 CI 全量静态仍报红。

**参考文档**：《工程化工具包说明》§4.2 选测段、《测试规范》「被测物与执行范围」节

## 4. 需求 14-3：护栏检查进程合并 <a id="r14-3"></a>

优先级：1（高）

**背景与动机**：10+ 个护栏检查各自以独立 Python 进程执行，每条都要付一次解释器启动与模块导入的固定成本，合计约 47s，占提交环 40%。检查数量增加时该成本线性叠加，而检查本身多为秒级以内的静态判定。

**内容**：

1. 新增 `engkit checks` 子命令：读取 `[[preflight.self_tests]]` 登记表，在**单进程**内按声明序逐条执行。
2. 执行方式：`runpy.run_path` 同进程运行脚本 + 临时替换 `sys.argv`，捕获 `SystemExit` 取退出码；**不要求脚本改造 `main` 签名**。
3. 隔离契约：每条执行前后恢复 `sys.argv` / `sys.path` / 环境变量快照；单条抛异常只记该条失败并继续后续条目；末尾汇总「通过 N / 失败 M」并列出失败标签。
4. 逐条保留耗时输出，口径与 `execute()` 一致（`通过（0.3s）`）。
5. 保留逐条子进程通路（配置 `runner = "process"`），供脚本存在模块级副作用或需要真实进程隔离时回退。

**完成标准**：同一份登记表在单进程模式下的总耗时显著低于逐条进程模式；某条检查抛未捕获异常时其余检查仍全部执行且整体退出码非零；单条失败不会被后续条目掩盖。

**参考文档**：《工具包开发约定》§2 代码约定、《AI开发规范》§5 补充纪律

## 5. 需求 14-4：度量基准与负向验收 <a id="r14-4"></a>

优先级：1（高）

**背景与动机**：本域全部改动都在「跳过」语义上做文章，一旦跳过逻辑本身错了，门禁会变绿而缺陷进主干——比慢更糟。因此验收必须同时证明「变快了」与「该拦的仍拦得住」，且耗时目标不得凭空设定。

**内容**：

1. **基准**：取一次真实推送的分步耗时（每步耗时 + 改动集规模），作为唯一基准口径；不采用临时 clone 冷启动数据（会系统性偏高），不采用历史日志重建（缺分步数据）。
2. **目标**：相对基准下降——推送环 ≥50%、提交环 ≥40%；绝对值待基准测出后回填至计划表，不回填前不宣称达标。
3. **负向验收 5 类注入**（全部须被拦，缺一不可）：
   1. 代码已变但输入指纹未变（模拟假命中）→ 必须重跑；
   2. 缓存文件损坏 / 不可写 → 必须回退真跑，且预检结论与无缓存时一致；
   3. 新增未登记步骤（`type` / `cmd` 未进推断表）→ fail-closed 报错，不得默认跳过；
   4. 真实缺陷注入（类型错误 / 覆盖率缺口 / 文档链接失效）→ 必须报红；
   5. 跨仓配置差异（两份不同的 `engkit.toml`）→ 不得互相命中。
4. **验收分两行**：本地（editable 路径依赖，改动即时生效）与 CI（从远端克隆 engkit，跟随 main 头）分别记录；engkit 未推送期间 CI 仍跑旧版，此前置依赖写入计划与实施记录，不得默认「已在 CI 生效」。

**完成标准**：5 类注入各有用例且全部按预期被拦；基准数据与达成数据同时留档（含改动集规模）；计划表两行验收均有结论。

**参考文档**：《AI开发规范》§7 红线与纪律、《测试规范》§6 覆盖率口径
